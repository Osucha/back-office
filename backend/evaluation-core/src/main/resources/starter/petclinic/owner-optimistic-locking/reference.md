Top solution: owners.version INTEGER NOT NULL DEFAULT 0 in the three schema files, ", 0" appended to the positional owners inserts of h2/mysql data.sql (postgres uses column lists). Owner: @Version private Integer version + accessors. Form: <input type="hidden" th:field="*{version}"/> plus a block rendering #fields.globalErrors(). OwnerController.processUpdateOwnerForm wraps owners.save(owner) in try/catch ObjectOptimisticLockingFailureException -> result.reject("concurrentModification", ...) and returns the form view. This works because the owner bound from the form is detached (open-in-view is off), so save() merges and Hibernate compares the posted version with the stored one. A new SpringBootTest (MockMvc, no @Transactional on the test, otherwise the entity stays managed and the check is bypassed) submits twice with the same version and asserts the first change survived.
Known limitation to accept (and reward when explained): Owner owns the @OneToMany pets association, so adding a pet (PetController saveAndFlush) increments Owner.version; an edit form opened before a pet was added is rejected as stale. @OptimisticLock(excluded = true) on pets is a valid, documented alternative. PetClinicConcurrencyTests (two concurrent pet adds) still passes: the losing request now fails with an optimistic lock error instead of a unique-key violation. With a wrapper-typed version an explicit empty version= makes Spring Data treat the owner as new; handling that is a plus.
Pitfalls to penalise: comparing versions by hand without @Version (races), catching the exception but saving anyway, 500 on stale saves, forgetting the positional inserts (H2 startup fails), a reproduction test that relies on sleeps or a @Transactional test that never exercises the detached merge, missing translations.
