# Performance: query review and load-test baseline

How the numbers were produced and how to reproduce them: [perf/README.md](../../perf/README.md).
SLOs: [09-scale-and-operations.md](09-scale-and-operations.md) (p95 of reads < 300 ms, availability 99.9 %,
event delivery p95 < 2 s).

> **Laptop baseline, 2026-09-28.** Windows 11 laptop, Docker Desktop (WSL2) PostgreSQL 17
> (`shared_buffers=512MB`, `work_mem=16MB`), one API JVM (`-Xmx1g`, filesystem BlobStore), k6 in Docker
> on the same machine. **The CPU was saturated (100 % load) by four other parallel Gradle builds during
> the measurements**, so absolute numbers are pessimistic and noisy (±50 % between runs of the same
> plan). Use them as a floor to compare against on the same kind of machine, not as capacity figures;
> re-measure on a cluster install before sizing.

## Dataset

Generated by `PerfDataGenerator` (`backend/app/src/test/kotlin/pl/mos/backoffice/app/perf`), set-based SQL:

| Table | Rows | Shape | Seed time |
|---|---:|---|---:|
| `project` | 50 | | 0.02 s |
| `workflow_run` | 200 000 | 365 days, skewed towards low-numbered projects (quadratic), 70 % succeeded / 20 % failed / 9 % cancelled / ~1 % active | 44 s |
| `artifact` | 49 806 | 1 per 4 runs, inline | 8 s |
| `approval_request` | 20 569 | 1 per 10 runs + every waiting gate (OPEN) | 5 s |
| `ci_execution` | 77 696 | CI-triggered runs + 1 in 6 others | 8 s |
| `usage_record` | 2 000 000 | 365 days, 8 models (skewed), 5 context kinds, project on 60 % | 353 s |
| `audit_log` | 1 000 000 | 365 days, 12 operations, 200 actors (monthly partitions, V404) | 367 s |

The full size was kept (no reduction needed); a smaller run is `-Dperf.runs=50000 -Dperf.usage=500000`.
"Member" queries use a `ProjectFilter.Only` of 5 projects including the largest one.

## Index review

`./gradlew :app:perfTest` — median of 5 `EXPLAIN (ANALYZE, BUFFERS)` runs, warm cache. "Before" = with the
indexes of the review migrations dropped in a rolled-back transaction, "after" = with them. Full plans in
`backend/app/build/perf/query-plans.md` after a run.

### Added indexes (only indexes, no semantic change)

| Migration | Index | For |
|---|---|---|
| projects `V104__query_review_indexes.sql` | `idx_workflow_run_status_created (status, created_at DESC)` | runs list filtered by status, newest first (admin and member), recovery / active-run scans |
| llm-gateway `V2__usage_query_indexes.sql` | `usage_record_occurred_covering_idx (occurred_at) INCLUDE (cost, tokens…, model_label, context_kind)` | usage summaries by DAY / MODEL / CONTEXT_KIND and the monthly total: index-only scans instead of bitmap heap scans |
| llm-gateway `V2` | `usage_record_project_occurred_idx (project_id, occurred_at DESC) INCLUDE (…) WHERE project_id IS NOT NULL` | per-project usage summary and entries list |
| identity `V405__audit_query_indexes.sql` | `audit_log_result_idx (result, event_time DESC)` (partitioned) | audit search "result = DENIED/FAILURE" |
| projects `V103__artifact_blobs.sql` | `idx_artifact_blob_run`, `idx_artifact_inline_large` (partial) | retention job and the legacy-artefact migration |

The V104 / V2 indexes are created without `CONCURRENTLY` (Flyway holds a lock that a concurrent build
waits on forever); on a large existing install create them beforehand with
`CREATE INDEX CONCURRENTLY IF NOT EXISTS <same name> …` and the migration becomes a no-op.

### Measured effect (ms, median)

| Query | Before | After | Plan change |
|---|---:|---:|---|
| runs list, admin, `status=FAILED`, page 1 | 0.36 | 0.23 | `idx_workflow_run_created_at` + filter → `idx_workflow_run_status_created` |
| runs list, member, `status=FAILED`, page 5 | 4.91 | 1.29 | same |
| usage summary by DAY, 30 days (dashboard) | 2 049 | 1 021 | bitmap heap scan → index-only scan |
| usage summary by MODEL, 30 days | 700 | 318 | same |
| usage summary by MODEL, one project, 30 days | 279 | 26 | BitmapAnd of two indexes → `usage_record_project_occurred_idx` |
| usage total cost this month (dashboard) | 458 | 175 | bitmap heap scan → index-only scan |
| usage entries of a project, page 1 | 1.87 | 0.31 | `occurred_at` index + filter → project index |
| usage summary by DAY, 365 days | 27 568 | 20 691 | seq scan both times (whole table) |
| audit search `result=DENIED` | 2.04 | 0.87 | PK walk of every partition → `audit_log_result_idx` |

### Queries already well served (no change)

| Query | ms | Plan |
|---|---:|---|
| runs list admin / member / one project, page 1–5 | 0.2–0.5 | `idx_workflow_run_created_at` / `idx_workflow_run_project_created` |
| runs list, active runs (admin / member) | 1.6–4.5 | index scans, bitmap on `idx_workflow_run_project_status` |
| run detail (run + artefacts) | 0.3 | PK + `idx_artifact_run` |
| approvals inbox admin / member, approval of a run | 0.2–0.8 | `idx_approval_request_status_project_created`, `…_project_status`, `…_run` |
| CI executions list admin / project / member, idempotency lookup | 0.1–0.4 | `idx_ci_execution_created`, `…_project_created`, `…_key` |
| audit search: no filter, next page (keyset), operation, actor, entity, project + 7 days | 0.6–1.0 | Merge Append of per-partition PK / partitioned indexes; time ranges prune partitions |
| dashboard counters (open approvals, active runs, waiting for CI, failed 7 days, recent runs / CI) | 0.2–15 | index-only scans |

Keyset paging over the partitioned `audit_log` stays an ordered Merge Append of per-partition primary-key
scans (`LIMIT 51` reads ~51 rows), verified by `AuditPartitioningTest`.

### Findings that need more than an index (not done here: semantic / code changes)

1. **Usage summaries over long ranges are the bottleneck.** DAY grouping over 30 days is ~1 s on this
   dataset even index-only (the `to_char(date_trunc(…))` per row and hashing ~165k rows), and the
   dashboard issues it on every load; 365 days takes ~20 s. Recommended: a daily rollup table
   (`usage_daily(day, provider, model_label, context_kind, project_id, sums…)`) maintained on insert or
   by a RETENTION-style job, and summaries reading the rollup for whole days plus the raw table for today.
   Cheaper interim step: group by `date_trunc('day', occurred_at AT TIME ZONE 'UTC')` and format in Kotlin.
2. **`count(*)` for page totals** of the unfiltered runs list (93 ms at 200k rows) and CI executions (41 ms)
   grows linearly. Keyset paging with "has more" (like the audit search) or an estimated count
   (`pg_class.reltuples`) above a threshold would make it constant.
3. **Audit rows outside the created partitions** (imports, backfills) land in `audit_log_default`; the
   identity retention job now creates the partition of every month found there and moves the rows.

counts those as held, see `sse.js`.)

**Reading the baseline.** No request failed in any scenario, every CI execution completed, and 50 SSE
subscribers did not break the API. Latency SLOs are not met on this machine: the host CPU was saturated
by parallel builds, which inflates every number (the single-user run shows the per-request cost: runs list
p50 319 ms, run detail 157 ms). The dashboard is the clear outlier independent of load (≥ 2 s with one
user) because of the usage DAY summary (finding 1); fix that before the next baseline. Re-run on an idle
machine or a cluster (medium size, doc 09) to get figures to hold releases against.

## Artefact storage

- Artefacts above `backoffice.storage.artifacts.inline-max-bytes` (64 kB) are written to the BlobStore
  (`runs/<runId>/artifacts/<artifactId>`); the row keeps `blob_key`, `size_bytes`, `sha256` and an empty
  `content` (V103). Edits write a new key (`….<sha256 prefix>`), superseded keys go to `run_blob_gc` and
  are deleted by the retention job; reads go through a per-replica Caffeine cache (64 MB) keyed by the
  immutable blob key, so a run detail does not hit object storage on every request.
- **Existing large rows** are migrated by the projects retention job (`migrate-inline-artifacts`, 200 per
  pass, oldest first) rather than on read: reads are often in read-only transactions, and a background
  job bounds the object-storage write rate. Until moved, such rows are served inline as before.
